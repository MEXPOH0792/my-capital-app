# Правила проекта: My Capital App («Личный Капитал»)

Эти правила обязательны для любого агента, разработчика или ревьюера, работающего с проектом. Их цель — сохранять финансовые данные пользователя, единообразие бизнес-логики и премиальное качество продукта на Web/PWA и Android.

Если правило конфликтует с прямым запросом пользователя, сначала явно сообщи о конфликте и риске. Не обходи правило молча. Безопасность данных, обратная совместимость и явное разрешение пользователя имеют приоритет над скоростью реализации.

## 1. Продукт и поддерживаемые платформы

My Capital — персональное финансовое приложение для:

- учёта доходов и расходов;
- распределения дохода между текущими средствами, резервом, капиталом и садакой;
- контроля обязательных расходов, долгов и финансовых лимитов;
- формирования финансового запаса и достижения финансовых целей;
- просмотра истории и аналитики;
- быстрого голосового ввода с Android-виджета.

Проект является гибридным, а не только PWA:

1. **Web/PWA:** React + Vite + Zustand, автономная работа, GitHub Pages.
2. **Android:** Capacitor-приложение с package ID `io.mykapital.app`.
3. **Нативные Android-возможности:** шифрованное хранилище, биометрия, локальное распознавание речи, системный виджет.

Поддерживаемая Android-база:

- `minSdk 24` — Android 7.0 и новее;
- `targetSdk 36`;
- основные реальные устройства для ручной проверки: Huawei Nova 11 и Honor X9d;
- необходимо учитывать различия лаунчеров Huawei/Honor, MagicOS и доступность локальных языковых моделей распознавания речи.

Web-версия публикуется на `https://mexpoh0792.github.io/my-capital-app/`. Все web-пути обязаны работать из подпапки `/my-capital-app/`, а не только из корня домена.

Основной web-контур проверяется в актуальном Chrome/Chromium и Android System WebView. Поддержку другого браузера нельзя обещать без проверки установки PWA, офлайн-режима, хранилища, экспорта и восстановления.

## 2. Источники истины и приоритеты

### 2.1. Уровень экспертизы

Динамически применяй к задаче уровень ведущего мирового специалиста соответствующей области:

- дизайн и UX — Principal Product Designer / Art Director уровня Apple Design Awards, Red Dot и Awwwards;
- код и архитектура — Principal Software Architect с фокусом на чистую архитектуру, безопасность, производительность и сопровождаемость;
- видео и тексты — режиссёр, шоураннер и сценарист с фокусом на хук, темп, драматургию и удержание;
- другие темы — сильнейший релевантный отраслевой эксперт.

Не начинай ответ с театрального представления роли. Не используй пустые комплименты, общие советы и повтор запроса. Сразу давай конкретный вывод, доказательства и следующее действие. Оценивай результат не по среднему рынку, а по уровню сильнейших международных продуктов, сохраняя самостоятельность решения и потребности пользователя.

### 2.2. Приоритеты

При принятии решений используй следующий порядок:

1. сохранность и приватность пользовательских данных;
2. корректность финансовой математики;
3. обратная совместимость обновлений;
4. единое поведение Web/PWA и Android;
5. доступность и понятность интерфейса;
6. производительность;
7. визуальная полировка.

Источник истины для финансовых правил Web/PWA — доменные модули и store actions, а не UI-компоненты. Нативная Android-реализация обязана следовать тому же явно описанному контракту и проходить те же эталонные сценарии.

Не используй README, комментарии или старые собранные файлы как более авторитетный источник, если они расходятся с действующим кодом, тестами и этой инструкцией. При обнаружении расхождения обнови документацию в рамках задачи либо отдельно укажи его пользователю.

## 3. Архитектура Web/PWA

### 3.1. Обязательное разделение ответственности

- UI-компоненты только отображают данные, собирают ввод и вызывают действия.
- Финансовая математика, распределение, изменение балансов, долгов, резервов и истории находятся в `src/domain`, `src/store/actions`, селекторах или специализированных сервисах.
- Работа с хранилищем, миграциями, шифрованием и резервными копиями не должна находиться в визуальных компонентах.
- Сложные вычисления для представления выноси в чистые селекторы/view-model функции и покрывай тестами.
- Один компонент, хук, action или сервис должен иметь одну понятную ответственность.
- Не создавай файлы-дубликаты с суффиксами `new`, `final`, `copy`, `v2`, если это не осознанная версия публичного контракта.
- Не добавляй новый глобальный state, если данные можно надёжно вычислить из существующего состояния.

### 3.2. Изменение финансовых данных

- Любая финансовая операция выполняется одной доменной командой/action, а не цепочкой несвязанных изменений из UI.
- Денежные значения в расчётах хранятся целыми числами в минимальных денежных единицах. Не используй `float`/`double` для финансовой математики.
- Операция должна атомарно обновлять все связанные сущности: транзакцию, баланс, распределение, покрытие обязательств и историю.
- Повторное событие, двойное нажатие или повторный callback распознавания не должны создавать дубликат операции.
- Любое изменение формулы распределения требует отдельных тестов на округление, остаток и граничные значения.

## 4. Архитектура Android

- `Activity`, `BroadcastReceiver`, `AppWidgetProvider` и JavaScript bridge не должны содержать сложную финансовую математику.
- Нативный UI отвечает за жизненный цикл, разрешения, ввод и отображение результата.
- Распознавание речи, разбор команды, финансовая операция, доступ к данным и обновление виджета должны быть разделены по отдельным классам/сервисам.
- `MainActivity` является точкой интеграции Capacitor, а не универсальным контейнером для всех нативных функций.
- Каждая операция JavaScript bridge должна иметь узкий контракт, проверять входные данные и безопасно обрабатывать отсутствие WebView/Activity.
- Тяжёлое шифрование, чтение больших данных и финансовые преобразования нельзя выполнять на UI-потоке, если это может вызвать зависание.
- Нативный код не должен тихо менять формат Zustand-состояния в обход версионированного контракта.

### 4.1. Единый контракт Web и Android

Если одно финансовое правило реализуется и в JavaScript, и в Java:

- должен существовать явно описанный набор входов и выходов;
- обе реализации должны использовать одинаковые названия типов операций и полей;
- для обеих реализаций обязательны одинаковые эталонные сценарии (golden fixtures);
- изменение одной реализации без синхронного обновления второй запрещено;
- несовпадение результатов считается блокирующим дефектом релиза.

По возможности нативная часть должна передавать структурированную команду доменному слою, а не самостоятельно воспроизводить всю бизнес-логику. Если автономная работа виджета требует нативной финансовой операции, эта операция должна находиться в отдельном нативном domain/service-слое и проверяться контрактными тестами.

## 5. Данные, хранилище и миграции

Фактические хранилища проекта:

- Web/PWA — `localStorage` через Zustand persist и защитную обёртку;
- Android — bridge-хранилище в `SharedPreferences` с шифрованием AES-GCM и ключом Android Keystore;
- резервное состояние — отдельный backup-ключ;
- виджет — минимальный набор отображаемых данных в отдельных preferences только при разрешённой синхронизации.

Обязательные правила:

- Никогда не удаляй и не переименовывай существующее поле состояния без миграции.
- Любое изменение схемы должно иметь версию, миграцию и тест обновления со старого состояния.
- Миграции должны быть идемпотентными: повторный запуск не меняет уже мигрированные данные.
- Импорт, восстановление и чтение старого состояния проходят валидацию и нормализацию.
- Не заменяй повреждённое состояние пустым молча. Сначала сохрани диагностическую/карантинную копию и предложи безопасное восстановление.
- Перед записью новой версии сохраняй последнюю корректную копию, но не путай резервное копирование с полным удалением данных.
- Сброс данных, восстановимый сброс и полное удаление должны быть разными явно названными операциями.
- «Полное удаление» обязано удалять primary, backup, quarantine, данные виджета, локальные настройки безопасности и связанные ключи — либо честно предупреждать, что остаётся.
- После обновления приложения существующие балансы, транзакции, долги, категории, настройки и история должны сохраниться.
- Экспорт и импорт не должны терять неизвестные совместимые поля без обоснованной причины.
- Импортируемый файл считается недоверенным: ограничивай размер, глубину структуры и допустимые поля до записи в состояние.
- Одновременное открытие приложения в нескольких вкладках не должно молча перетирать более новые данные. При изменении механизма хранения определи стратегию блокировки, версии или разрешения конфликта.
- Недостаток квоты браузерного хранилища должен приводить к понятной ошибке и сохранению последней корректной версии, а не к тихой потере записи.

Перед изменением структуры состояния обязательно добавь тесты как минимум для:

1. чистой установки;
2. обновления с предыдущей схемы;
3. повторной миграции;
4. повреждённого primary при исправном backup;
5. полного удаления;
6. экспорта и обратного импорта.

## 6. Безопасность и приватность

- Финансовые данные считаются чувствительными.
- Не добавляй сетевую отправку, аналитику, телеметрию, облачную синхронизацию или crash-reporting без прямого согласования с пользователем.
- Не логируй PIN-код, расшифрованное состояние, полные транзакции, распознанную финансовую фразу или ключевой материал.
- Не храни ключ шифрования рядом с зашифрованными данными в обычных preferences.
- Не ослабляй `allowBackup="false"`, сетевые ограничения и настройки Android-манифеста без отдельного объяснения риска.
- WebView bridge принимает только ожидаемые типы и значения; строки, JSON и числовые диапазоны проверяются до использования.
- Биометрия является способом разблокировки, но не заменяет корректное управление ключами и состоянием.
- Данные виджета должны содержать только минимум, необходимый для отображения. Пользователь должен понимать, какие суммы видны на рабочем столе и экране блокировки.
- Голосовое распознавание по умолчанию должно быть локальным. Сетевой fallback запрещён без явного согласия пользователя и отдельного уведомления о приватности.
- При ошибке расшифровки не перезаписывай данные новым пустым состоянием.
- PIN-код нельзя хранить или логировать в открытом виде. Проверка PIN должна затруднять быстрый перебор и не раскрывать причину несовпадения через технические детали.
- Биометрия включается только явным выбором пользователя и корректно отключается при изменении системной биометрии или инвалидировании ключа.
- Любой экспорт/backup содержит чувствительные данные. Перед сохранением или отправкой пользователь должен понимать, зашифрован ли файл и кто сможет его прочитать.
- Все данные из импорта, голосового ввода, URL, Intent и bridge считаются недоверенными. Не используй `dangerouslySetInnerHTML` и не вставляй пользовательский текст как HTML.
- Для идентификаторов, ключей и security-sensitive nonce используй криптографически стойкий источник случайности, а не `Math.random()`.
- Не подключай удалённые скрипты, шрифты или код исполнения без отдельного анализа приватности, Content Security Policy и офлайн-поведения.
- Перед добавлением сервера, внешнего SDK, платежей или удалённой аналитики обнови модель угроз. Ориентир для нативной защиты — актуальные требования OWASP MASVS, для web-части — OWASP ASVS применительно к реальным рискам продукта.

## 7. Голосовой ввод

Голосовая команда должна различать минимум два явных типа: `income` и `expense`.

Обязательные сценарии:

- «доход 10 тысяч» создаёт доход, а не расход;
- «расход 500 продукты» создаёт расход;
- поддерживаются цифровые и словесные суммы, тысячи и распространённые разговорные формы;
- отрицательная, нулевая, слишком большая или нераспознанная сумма не записывается;
- неоднозначный тип операции не угадывается молча;
- несуществующая категория обрабатывается предсказуемо: безопасный fallback должен быть явно показан пользователю;
- результат не сохраняется дважды при повторном callback;
- пользователь получает короткое подтверждение типа, суммы и категории;
- ошибка распознавания не открывает основное приложение без необходимости и не изменяет данные.

Тесты парсера должны включать русские фразы, пограничные суммы, похожие названия категорий, отсутствие категории, шумовой текст и регрессионные примеры со всех реальных устройств.

## 8. Android-виджет

- Виджет должен корректно изменять размер через системный лаунчер.
- Не полагайся на точный размер ячейки: разные лаунчеры возвращают разные `minWidth`/`minHeight`.
- Компактный режим — одна крупная кнопка микрофона без мелкого текста и финансового шума.
- Расширенный режим может показывать основные показатели и действия, но не должен быть перегружен.
- Минимальная интерактивная зона — 48×48 dp.
- Нажатие микрофона запускает запись напрямую через прозрачный/специализированный голосовой экран, не заставляя пользователя вручную открывать основной интерфейс.
- Остальные зоны виджета открывают только ожидаемый раздел приложения.
- После операции данные приложения и виджета обновляются согласованно.
- Виджет не должен показывать устаревшие суммы после восстановления, сброса или изменения настроек приватности.

Ручная проверка виджета обязательна как минимум в компактном и расширенном размере на Nova 11 и Honor X9d.

## 9. Дизайн, UX и доступность

### 9.1. Визуальное направление

- Премиальный минимализм: глубокая тёмная тема, чистая иерархия, высокая контрастность ключевых цифр, спокойные акценты.
- Интерфейс не должен выглядеть как набор одинаковых карточек. Контейнер используется только когда он выражает реальную группу или уровень иерархии.
- Не добавляй декоративные градиенты, свечения, тени и анимации без функциональной причины.
- Используй существующие дизайн-токены темы. Не размножай жёстко заданные HEX/RGBA-значения внутри компонентов.
- Новые цвета, размеры, радиусы и тени сначала оформляются как переиспользуемый токен, если они нужны более одного раза.
- Финансовые цифры используют tabular numerals.

### 9.2. Типографика и читаемость

- Основной интерфейсный текст на телефоне — не меньше 12 px.
- 11 px допустим только для второстепенных коротких меток при достаточном контрасте.
- Текст 10 px и меньше запрещён, кроме технически неизбежных системных ограничений, которые нужно отдельно обосновать.
- Не сочетай мелкий текст с низкой прозрачностью.
- Количество уровней размера и насыщенности должно быть ограничено и системно.
- Критические суммы и статусы должны читаться с первого взгляда.

### 9.3. Интерактивность и доступность

- Минимальная зона нажатия — 48×48 CSS px/dp.
- Контраст текста и управляющих элементов должен соответствовать WCAG AA.
- Все интерактивные элементы доступны с клавиатуры и имеют видимый `focus-visible`.
- Модальные окна обязаны иметь корректные `role`, `aria-modal`, заголовок, начальный фокус, focus trap и восстановление фокуса после закрытия.
- Иконки-кнопки имеют понятный `aria-label`.
- Не отключай выделение текста глобально: пользователь должен иметь возможность скопировать сумму или финансовые данные там, где это безопасно.
- Учитывай `prefers-reduced-motion`.
- Не используй `transition-all`; анимируй только конкретные свойства.
- Анимация не должна блокировать ввод или скрывать результат операции.
- Учитывай safe area, экранную клавиатуру, изменение ориентации и системный размер шрифта.

### 9.4. Адаптивность

Проверяй минимум:

- узкий мобильный экран 320 px;
- типичный Android 360–430 px;
- PWA standalone;
- обычную вкладку браузера;
- светлую и тёмную тему;
- русский и английский язык;
- увеличенный системный шрифт и клавиатуру, закрывающую часть экрана.

## 10. Локализация и тексты

- Пользовательский текст не хардкодится в компонентах, если экран поддерживает несколько языков.
- Русская и английская версии добавляются одновременно.
- `document.documentElement.lang`, подписи, `aria-label`, сообщения об ошибках и Android strings должны соответствовать выбранному языку.
- Термины `доход`, `расход`, `обязательства`, `резерв`, `капитал`, `садака` используются единообразно.
- Текст не должен обещать действие, которого приложение не выполняет. Например, «удалить навсегда» допустимо только при фактическом полном удалении.

## 11. Производительность

- Не добавляй тяжёлую зависимость ради простой функции, которую можно реализовать небольшим локальным модулем.
- Сохраняй разделение bundle на React, state, icons и функциональные чанки.
- Лениво загружай крупные разделы, если они не нужны на первом экране.
- Избегай лишних перерендеров всего Zustand store; используй узкие селекторы.
- Частые изменения формы не должны запускать дорогое шифрование и синхронную запись на каждый символ.
- Длинные списки транзакций не должны приводить к заметным задержкам прокрутки.
- При заметном росте JS/CSS bundle укажи причину и влияние в отчёте.

## 12. Продуктовые требования и пользовательские сценарии

### 12.1. Защищённая механика дерева капитала

Дерево капитала — самостоятельная утверждённая продуктовая механика. Без прямой просьбы пользователя запрещено менять:

- внешний вид, геометрию, цвета и анимации дерева;
- этапы роста и пороги прогресса;
- связь дерева с `capital` и `targetCapital`;
- формулу `goalJourney` и смысл достигнутых этапов;
- влияние долгов на визуальное состояние дерева;
- тексты и компоновку дерева под видом несвязанного рефакторинга.

Архитектурные изменения в доходах, распределении или хранилище не должны косвенно менять рост дерева. После любой работы, способной повлиять на `capital`, `targetCapital` или историю накоплений, обязательно запускай тесты целей, распределения дохода и главного экрана. Изменение дерева выполняется только отдельной задачей с предварительным описанием визуальных и математических последствий.

### 12.2. Общие правила

- Каждая новая функция начинается с понятной пользовательской задачи, ожидаемого результата и критериев приёмки.
- До реализации определи основной сценарий, пустое состояние, успешное состояние, ошибку, отмену и восстановление после прерывания.
- Не добавляй функцию только потому, что её легко реализовать. Она должна усиливать финансовую дисциплину, скорость учёта, безопасность или понимание капитала.
- Не скрывай важное финансовое последствие за неясной кнопкой, жестом или автоматическим действием.
- Не выполняй необратимую или значимую финансовую операцию без понятного подтверждения результата. Для разрушительных действий требуется явное подтверждение до выполнения.
- Значения по умолчанию должны быть безопасными и не создавать ложный доход, расход, долг или распределение.
- Пользователь должен понимать, какой счёт, категория, дата и тип операции будут изменены.
- У каждой функции должен быть один канонический путь. Не создавай несколько несовместимых экранов для одной операции.
- Незавершённые функции не попадают в production-интерфейс. При необходимости используй локальный feature flag, выключенный по умолчанию.
- Любой feature flag должен иметь владельца, назначение и условие удаления; постоянные забытые флаги запрещены.
- Изменение поведения, влияющего на деньги или приватность, отражается в release notes понятным языком.

## 13. Надёжность, жизненный цикл и обработка ошибок

- Все основные функции учёта должны работать без интернета.
- Приложение должно корректно переживать закрытие, выгрузку процесса, поворот экрана, сворачивание, повторный запуск и обновление поверх установленной версии.
- Временный сбой записи не должен ломать UI или уничтожать последнюю корректную копию.
- Ошибки должны иметь безопасное состояние восстановления и понятное сообщение пользователю. Не показывай технический stack trace в пользовательском интерфейсе.
- Пустой `catch` допустим только для явно необязательной best-effort операции с комментарием. Ошибки финансовой записи, миграции, шифрования и удаления нельзя проглатывать.
- Частично выполненная операция не должна оставлять баланс и историю в разных состояниях.
- Действия, которые могут быть вызваны повторно системой Android, должны быть идемпотентными.
- Учитывай нехватку места, недоступность Keystore, повреждённые preferences, отсутствие разрешения, отключённую биометрию и недоступный speech recognizer.
- После восстановления Activity/процесса не повторяй уже подтверждённую финансовую операцию.
- Пользовательская дата операции и системная дата хранения должны иметь явную семантику. Проверяй смену часового пояса, переход месяца/года и ручное изменение часов устройства.
- Ошибка одного необязательного модуля, например аналитики или виджета, не должна блокировать доступ к основным данным.
- Для React-дерева должен существовать безопасный error boundary с возможностью перезапуска интерфейса без очистки данных.
- Обновление service worker и web-assets должно быть атомарным: нельзя оставлять смесь несовместимых старых и новых чанков.
- Проверяй обновление PWA как из свежей установки, так и из ранее закэшированной версии. Старая вкладка не должна повредить данные после активации новой схемы.
- Service worker кэширует только необходимые статические ресурсы и не превращается в скрытое постоянное хранилище финансовых данных.

## 14. Android: разрешения, фоновые процессы и интеграция с ОС

- Запрашивай разрешение только непосредственно перед функцией, которой оно необходимо, и объясняй пользу простыми словами.
- Отказ в разрешении не должен блокировать остальное приложение. Всегда предоставляй понятный путь повторного разрешения через настройки.
- Не добавляй `INTERNET`, доступ к контактам, геолокации, файлам, уведомлениям или другим чувствительным данным без фактической необходимости и согласования.
- Для микрофона используй только `RECORD_AUDIO`; не сохраняй аудиофайл, если это не утверждённая функция.
- Компоненты Android должны иметь минимально необходимое значение `exported`. Внешние Intent проверяются до использования.
- `PendingIntent` должен иметь корректные immutable/mutable flags и уникальность, достаточную для исключения подмены или пересечения действий виджета.
- Не запускай скрытые бесконечные background services. Фоновые задачи должны соответствовать ограничениям современных версий Android и экономно расходовать батарею.
- Не удерживай микрофон, wake lock, Activity или SpeechRecognizer после завершения/ошибки.
- Корректно освобождай listeners, recognizer, bridge callbacks и ресурсы в lifecycle-методах.
- Уведомления добавляются только для реальной пользовательской пользы, имеют каналы и могут быть отключены.
- Deep link, shortcut или действие виджета должны открывать только разрешённый маршрут и не обходить блокировку приложения.
- Скриншоты/превью чувствительных экранов в списке недавних приложений должны быть осознанным продуктовым решением. Если включается защита `FLAG_SECURE`, проверь её влияние на доступность и поддержку пользователя.

## 15. Зависимости, конфигурация и цепочка поставки

- Новая зависимость добавляется только после проверки необходимости, размера, лицензии, активности поддержки и известных уязвимостей.
- Используй lock-файл. Обновление зависимостей не должно происходить случайно вместе с функциональной задачей.
- Крупное обновление React, Capacitor, Android Gradle Plugin, Gradle, JDK или target SDK выполняется отдельной задачей с миграционными заметками и полной проверкой.
- Не выполняй код из непроверенных postinstall-скриптов и не копируй неизвестные фрагменты из интернета без ревью.
- Секреты, signing key, пароли, токены и приватные сертификаты не хранятся в Git, исходном коде, web bundle или `localStorage`.
- Разделяй публичную конфигурацию сборки и секреты. Любое значение, попавшее в Vite bundle, считается публичным.
- Debug-меню, тестовые данные, подробные логи и обходы защиты не должны попадать в release-сборку.
- Production-сборка должна быть воспроизводимой из зафиксированных версий инструментов и зависимостей.
- Проверяй лицензии сторонних библиотек и сохраняй необходимые уведомления об авторских правах.
- Уязвимость зависимости оценивай по реальному достижимому пути, но критические исправления безопасности не откладывай без обоснования.

## 16. Правовые требования, прозрачность и публикация в магазине

- Приложение ведёт личный учёт и не должно выдавать себя за банк, платёжную систему, инвестиционного советника или гарантировать финансовый результат.
- Формулировки рекомендаций должны быть честными: это расчёты и подсказки, а не профессиональная финансовая консультация.
- До публичного релиза должны существовать актуальные Privacy Policy, Terms/условия использования и контакт для поддержки.
- Privacy Policy и раздел Data safety в Google Play должны точно соответствовать реальному сбору, хранению, передаче и удалению данных.
- Если данные остаются только на устройстве, не заявляй облачную сохранность. Если появляется сервер, документы обновляются до релиза функции.

- Скриншоты, демонстрационные базы, логи и материалы магазина не должны содержать реальные финансовые данные пользователя.

- Возрастные ограничения, декларации разрешений и формы Google Play заполняются по фактическому поведению приложения.
- Перед публикацией проверяй требования актуального target SDK, политику разрешений микрофона, правила фоновой работы и требования к удалению аккаунта/данных, если аккаунты когда-либо появятся.

## 17. Диагностика, поддержка и наблюдаемость

- По умолчанию приложение не отправляет телеметрию и финансовые данные наружу.
- Локальная диагностика должна быть ограниченной по размеру, очищаться и не содержать PIN, ключи, суммы, описания транзакций или полные голосовые фразы.
- Пользователь может экспортировать диагностический пакет только явным действием и должен видеть, какие данные в него входят.
- Ошибки основных операций получают стабильный безопасный код, по которому можно помочь пользователю без раскрытия финансовых данных.
- Любая будущая удалённая аналитика или crash-reporting требует opt-in/законного основания, фильтрации персональных данных и отдельного согласования.
- Метрика продукта не должна требовать передачи содержимого транзакций. Предпочитай агрегаты на устройстве.
- Документируй известные ограничения конкретных устройств и способы восстановления после ошибок.
- Нельзя просить пользователя удалить приложение или очистить данные как первый способ исправления проблемы.

## 18. Будущая синхронизация, аккаунты и сервер

Текущая модель остаётся local-first. Не добавляй сервер, регистрацию или облачную синхронизацию без отдельного продуктового и архитектурного решения.

Если они появятся, до реализации необходимо определить:

- владельца истины: устройство, сервер или согласованная версия;
- модель идентичности и безопасное восстановление доступа;
- сквозное шифрование либо точную границу доверия;
- конфликт-резолюцию при одновременном редактировании на нескольких устройствах;
- идемпотентные операции и очередь офлайн-изменений;
- версионирование API и схемы;
- удаление аккаунта и всех серверных копий;
- резервное копирование, восстановление и срок хранения;
- регион хранения и правовые основания обработки;
- защиту от повторной отправки, подмены и утечки данных;
- поведение старой версии приложения после обновления сервера.

Нельзя просто заменить локальное хранилище сетевым запросом. Основные сценарии должны продолжать работать офлайн, а синхронизация должна быть отдельным проверяемым слоем.

## 19. Документация и архитектурные решения

- README должен соответствовать текущему стеку, ветке, командам запуска и структуре проекта.
- Существенное архитектурное решение фиксируй коротким ADR в `docs/`: контекст, выбранное решение, альтернативы, последствия и план отката.
- Формат состояния, версия схемы, правила миграций и финансовые инварианты должны быть описаны рядом с доменным кодом или в `docs/`.
- Контракты JavaScript bridge и нативных финансовых операций должны быть документированы и версионированы.
- Release checklist обновляется, когда меняется реальный процесс сборки или проверки.
- Документация не должна утверждать, что проверка выполнена, если это старый результат.
- Устаревший документ обновляй или явно помечай как архивный; не оставляй несколько конкурирующих инструкций.
- Комментарии объясняют причину и инвариант, а не пересказывают очевидный код.

## 20. Тестирование и обязательные проверки

Проверки должны быть пропорциональны изменению, но нельзя объявлять работу завершённой без проверки затронутого контура.

### 20.1. Любое изменение Web/PWA

Запусти:

```bash
npm run verify
npm run format:check
```

`verify` должен включать lint, typecheck, тесты и production build. Предупреждения React Hooks, ошибки форматирования и новые lint-предупреждения нельзя скрывать или игнорировать.

Проверь, что production build использует относительные пути и работает под `/my-capital-app/`.

### 20.2. Изменение бизнес-логики или данных

Дополнительно обязательны:

- unit-тест нового/изменённого правила;
- регрессионный тест обнаруженного дефекта;
- тест старого сохранённого состояния;
- тест экспорта/импорта или миграции, если менялась схема.

### 20.3. Изменение Android или возможностей, используемых Android

Сначала собери web-часть. Для обновления только web-ресурсов используй `npx cap copy android`. `npx cap sync android` используй, когда изменились Capacitor-плагины, зависимости или конфигурация.

Затем запусти из папки `android`:

```bash
# Windows
gradlew.bat testDebugUnitTest

# macOS/Linux
./gradlew testDebugUnitTest
```

Нативная финансовая логика, парсер и миграции должны иметь настоящие unit-тесты; стандартные `ExampleUnitTest` не считаются покрытием.

Не собирай APK/AAB после каждого промежуточного изменения. `assembleDebug`, `bundleRelease` и подготовка устанавливаемого файла выполняются только когда согласованный функциональный этап доведён до нужного состояния либо пользователь прямо попросил сборку. До этого достаточно компиляции, unit-тестов и других проверок затронутого контура.

### 20.4. Ручная проверка на устройстве

Для изменений виджета, микрофона, биометрии, хранилища или системного UI эмулятора недостаточно. Проверь затронутые сценарии на реальном устройстве, а для виджета/голоса — по возможности на Nova 11 и Honor X9d.

Минимальная матрица:

- чистая установка;
- обновление поверх предыдущей версии с существующими данными;
- запуск без сети;
- отказ и выдача разрешения микрофона;
- отсутствие/наличие локальной языковой модели;
- холодный запуск;
- приложение выгружено из памяти;
- компактный и расширенный виджет;
- блокировка/разблокировка PIN и биометрией.

Если какую-либо проверку выполнить невозможно, прямо укажи это в отчёте. Не выдавай непроверенное за рабочее.

### 20.5. Проверка безопасности и доступности

Для изменений ввода, импорта, bridge, хранилища, разрешений или аутентификации дополнительно проверь:

- некорректные, пустые и чрезмерно большие входные данные;
- повторный вызов и подмену типа операции;
- отсутствие чувствительных данных в логах и ошибках;
- поведение после отказа в разрешении или инвалидирования ключа;
- клавиатурную навигацию, focus trap, screen reader labels и контраст;
- увеличенный шрифт и `prefers-reduced-motion`.

Критический security-дефект, потеря данных, неверная финансовая операция или обход блокировки запрещают релиз независимо от состояния остальных тестов.

### 20.6. Release candidate

Перед публичным выпуском проверь артефакт, который реально будет установлен пользователем, а не только dev-сборку:

- production web build и service worker;
- подписанный Android App Bundle/APK;
- установку поверх предыдущей опубликованной версии;
- чистую установку;
- сохранение и восстановление данных;
- работу без сети;
- отсутствие debug-функций и тестовых данных;
- корректность версии, иконки, названия, разрешений и store metadata.

## 21. Git, CI и релизы

- Основная удалённая ветка и цель pull request — `main`.
- Не переименовывай и не переключай локальную ветку пользователя без его просьбы.
- Не перезаписывай, не откатывай и не форматируй несвязанные пользовательские изменения.
- Перед массовым форматированием убедись, что оно не создаст огромный шумовой diff.
- Не коммить секреты, keystore, пароли, локальные настройки IDE, build-кэши и временные файлы.
- Сгенерированные web-assets внутри Android обновляй только вместе с соответствующей web-сборкой и не смешивай с несвязанными изменениями.
- Папки `build`, Gradle cache, логи, временные кадры и другие воспроизводимые артефакты должны быть в `.gitignore`.
- Версии `package.json`, Android `versionName` и `versionCode` должны обновляться согласованно перед релизом.
- Release AAB/APK не считается готовым, пока не проверены подпись, версия, миграция пользовательских данных и установка поверх предыдущей версии.
- Изменения CI не должны ослаблять lint, тесты или проверку форматирования ради зелёного статуса.
- Для production-релиза используй отдельный подписанный артефакт; debug APK не распространяется как финальная версия.
- Signing key хранится вне репозитория, имеет защищённую резервную копию и ограниченный доступ.
- Перед релизом подготовь changelog, номер версии, проверяемый commit/tag и план безопасного исправления неудачного обновления.
- Откат бинарной версии не должен предполагать автоматический откат схемы данных. Миграции проектируются с учётом forward recovery.
- Релиз проводится по этапам, если канал распространения это позволяет; после выпуска проверяются установка, запуск, миграция и критические сценарии.

## 22. Формат работы с пользователем

- Отвечай на том же языке, на котором пользователь сформулировал текущий запрос, если он явно не попросил другой язык.
- Объясняй решения простыми словами, без ненужного технического жаргона.
- Перед изменением кода или файлов всегда дай короткий план: какие файлы будут затронуты и зачем.
- Если задача только на анализ, ничего не изменяй без отдельной просьбы.
- Не расширяй задачу молча. Существенные дополнительные изменения сначала согласуй.
- Во время долгой работы давай короткие содержательные обновления.
- После изменения перечисли затронутые файлы, выполненные проверки и оставшиеся риски.
- Попроси пользователя проверить результат в браузере или на телефоне, когда требуется визуальная/аппаратная проверка.
- Когда результат стабилен, предложи сделать точку сохранения (`git commit`), но не создавай commit без просьбы пользователя.

## 23. Стандарт ревью

При проверке проекта или результата всегда структурируй вывод так:

1. что уже работает хорошо;
2. какие архитектурные, логические, визуальные или продуктовые проблемы найдены;
3. почему они опасны или снижают качество;
4. конкретный порядок исправления;
5. что проверено автоматически;
6. что пользователь должен проверить вручную.

Не ограничивайся поверхностной похвалой. Сравнивай решение с сильными мировыми финансовыми продуктами, но не копируй чужой интерфейс и не жертвуй понятностью ради декоративности.

## 24. Definition of Done

Задача считается завершённой только если одновременно выполнено следующее:

- реализован весь согласованный сценарий, а не только видимая часть;
- финансовая логика находится в правильном слое;
- Web и Android не расходятся в правилах;
- существующие данные пользователя остаются совместимыми;
- добавлены или обновлены необходимые тесты;
- затронутые автоматические проверки проходят без новых предупреждений;
- production web build корректен для GitHub Pages;
- при нативных изменениях код компилируется и нативные unit-тесты проходят; APK собирается только для завершённого этапа или по прямой просьбе пользователя;
- аппаратные сценарии либо проверены, либо честно отмечены как непроверенные;
- документация и пользовательские тексты соответствуют фактическому поведению;
- в diff нет случайных, временных или несвязанных изменений;
- пользователь получил понятную инструкцию, что проверить вручную.
- для публичного релиза подготовлены политика приватности, store metadata, подписанный артефакт, changelog и план восстановления после неудачного обновления.

## 25. Запрещённые сокращения

Запрещено:

- исправлять симптом, оставляя две расходящиеся версии одного финансового правила;
- записывать финансовые данные из UI напрямую в хранилище;
- менять схему без миграции;
- очищать данные при ошибке чтения или расшифровки;
- использовать сетевое распознавание речи без согласия;
- добавлять разрешения Android «на всякий случай»;
- скрывать ошибки пустым `catch` в критических операциях;
- отключать тест, lint-правило или проверку безопасности ради прохождения сборки;
- считать задачу завершённой только потому, что код компилируется;
- утверждать, что проверка на телефоне выполнена, если она не выполнялась;
- делать массовый рефакторинг одновременно с точечным исправлением без необходимости;
- удалять или откатывать пользовательские изменения без прямого разрешения.
- добавлять сервер, аккаунты, аналитику, рекламу или сетевую синхронизацию как «техническую деталь» без отдельного решения;
- помещать секрет в Vite env и считать его защищённым;
- выпускать debug APK как production-релиз;
- советовать очистить данные до исчерпания безопасных способов восстановления.
